# Data model

> **Purpose:** the single reference for tables, types, precision, and constraints. Mirrors `src/infra/db/schema.ts`; when they disagree, fix one in the same PR.
> **Audience:** anyone touching the database. **Belongs here:** schema detail. **Lives elsewhere:** why (adr/), behavior (EXECUTION.md).

## Conventions

- `id text PK DEFAULT gen_random_uuid()` (Better Auth tables get app-generated text ids); `created_at`/`updated_at timestamptz` (append-only tables have `created_at` only). Exceptions keyed naturally: `job_runs.name`, `company_fundamentals.symbol`; `market_cap_entries` has no id (UNIQUE(snapshot_id, rank)).
- `ledger_entries`, `fills`, `order_events` carry a `BEFORE UPDATE OR DELETE` trigger (`forbid_mutation()`, migration 0001) that rejects mutation regardless of the connecting role; production additionally drops UPDATE/DELETE grants for the application role. Append-only is structural.
- Foreign keys are `ON DELETE RESTRICT` except identity-owned rows (sessions, auth_accounts, watchlists → users; watchlist_items → watchlists; market_cap_entries → market_cap_snapshots), which cascade.
- **Numeric types:** money `NUMERIC(18,2)`; prices `NUMERIC(18,4)`; quantities `BIGINT` (whole shares); position cost-basis `NUMERIC(20,4)`. Drizzle maps NUMERIC to strings → Decimal; **never JS number**.
- No DB trigger reproduces the order-transition table — the domain machine owns transitions; the DB keeps structural constraints only.

## Reset flow

Cancel eligible open orders at the venue (await terminal events or timeout → reconcile) → lock the account, mark its PENDING cash_transfers CANCELED (holds released, nothing posted — ADR-015) and set account + broker_account ARCHIVED in one transaction → create new account (PROVISIONING) → `provisionAccount()` → fund → DEPOSIT entry → ACTIVE. History remains queryable under the archived account. Nothing is deleted.

## Migrations

drizzle-kit generates SQL into `drizzle/` (committed, sequential, immutable once merged). Local: `pnpm db:migrate`. CI applies all migrations from zero on every run (validation). Production migrations are an explicit approval-gated release step — never automatic on cold start. Philosophy: roll forward; destructive operations (DROP, type narrowing, data rewrites) require a `-- destructive: <justification>` header, human sign-off, and a backup (pg_dump or Neon branch) first.
