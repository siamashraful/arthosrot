# ADR-015 — Paper cash transfers: simulated deposits and withdrawals with venue-settled posting and withdrawal holds

**Status:** accepted (2026-10)

**Context:** Paper accounts could only be funded once, at provisioning (the opening deposit, gated on venue settlement — INTEGRATIONS.md). Users asked to add or take out simulated cash without resetting. Money movement is the most correctness-sensitive feature after execution: a transfer must never let ledger cash exceed venue cash, a pending withdrawal must not be spendable twice (once by the withdrawal, once by a buy), a settlement must never post twice, and a reset must never leave a hold behind. The live-funding seam (`core/funding` `FundingProvider`, ADR-011) exists but is a LIVE-money port that may not be implemented without the live-trading ADR — reusing it for paper would blur the paper/live line.

**Decision:**

1. **A separate, paper-only module `core/cash-transfers`** with its own ports: `CashTransfersRepository`, `BuyReservationReader` (orders' Σ open BUY reservations), and `CashTransferVenue` (`initiate` / `getTransfer` / `listTransfers` / `cancelTransfer`) implemented by the two paper venues — `DeterministicPaperBroker` and `AlpacaPaperBroker` (sandbox). `core/funding` is untouched and still unimplemented. No live code, hostname or credential is added; `accounts.mode` stays PAPER-only.
2. **Table `cash_transfers`** (migration 0006): one mutable state row per request — `PENDING → SETTLED | FAILED | CANCELED`, terminal states have no exits. `UNIQUE(account_id, idempotency_key)` + a stored request fingerprint (`DIRECTION:amount`, canonical Money string) make replays safe and body-mismatched replays a 409 `IDEMPOTENCY_CONFLICT`. `venue_transfer_id` is UNIQUE. CHECKs: `amount > 0`; `settled_at IS NOT NULL ⇔ state = 'SETTLED'`.
3. **Deposits post only when the venue settles them** (same rule as the opening deposit). A pending deposit raises neither cash nor buying power.
4. **Withdrawals hold at request time.** Under the account `FOR UPDATE` lock: `withdrawable = cash − Σ open BUY reservations − Σ PENDING withdrawals` (floored at 0.00) is re-checked and the PENDING row inserted; the hold takes effect at that commit. **Buying power at placement (and in the portfolio view) now also subtracts PENDING withdrawals** (FINANCIAL_INVARIANTS.md invariant 5 formula). The negative `WITHDRAWAL` ledger entry posts at SETTLED; FAILED/CANCELED releases the hold and posts nothing.
5. **Exactly-once settlement.** Every state change runs under account → transfer `FOR UPDATE` locks (extends the global lock order: account → {order → position | transfer}); the transition re-checks PENDING; the ledger entry carries `ref_type = 'CASH_TRANSFER'`, `ref_id = transfer id`, and a partial UNIQUE index on `ledger_entries(ref_id) WHERE ref_type = 'CASH_TRANSFER'` is the structural backstop. The venue's record must match the local direction + amount or nothing posts.
6. **Venue semantics.** Deterministic: settles synchronously inside the request (CI/E2E/local depend on it); test hooks simulate async ACH, venue failure, definitive rejection, ambiguous timeout and a venue restart. Alpaca sandbox: ACH `INCOMING` (deposit) / `OUTGOING` (withdrawal) on the account's existing ACH relationship (listed and reused; created only if none is usable); status polled via the transfers list (paged; the API documents list, not get-by-id). Only `COMPLETE` settles; `QUEUED/APPROVAL_PENDING/PENDING/SENT_TO_CLEARING/APPROVED` and unknown statuses stay PENDING; `REJECTED/CANCELED/RETURNED` fail with the venue's reason. A 4xx on initiate is a definitive rejection (FAILED, hold released); a 5xx/timeout is ambiguous — the row stays PENDING (hold kept) and the sweep later links the venue transfer or fails it. **Recovery rules (2026-10 hardening):** recovery only runs past the 10-minute grace window; a candidate must match direction + amount, be unlinked, and have been created within **± 5 minutes** (`RECOVERY_WINDOW_MS`) of the local row — the closest in time wins. Because grace > window, a newer request whose venue call is still in flight (venue transfer created ≈ now) can never be claimed by an older row. `listTransfers` never lists the venue account's **opening funding transfer** (Alpaca: the account's oldest INCOMING transfer — `provisionAccount` posts it before any user transfer can exist; deterministic: funding is not a transfer record), so it can never be linked and double-posted. Adapters skip unreadable venue rows one by one (bad date, amount or direction; logged) and report the listing `complete: false`; absence from an incomplete listing proves nothing, so the row stays PENDING (hold kept, logged every pass) instead of failing — failing a transfer the venue executed would let the ledger exceed venue cash. `getTransfer` remains authoritative by id (an unreadable matching row throws: ambiguous, never "no record").
7. **Settlement drivers:** the user's own `GET /api/v1/account/cash` (opportunistic, never errors on venue failure — like `getMe → tryActivate`) and the worker's reconciliation pass (`sweepPending`, alongside `activatePendingAccounts`). Each pass reads the venue's transfer list **once per account** and resolves every PENDING row from it; only a linked id missing from the listing falls back to the by-id lookup.
8. **Limits (domain rules, enforced for every venue):** min 1.00, max 50,000.00 per transfer, and ≤ 50,000.00 deposited per account in any trailing 24 h — PENDING + SETTLED transfer deposits **plus the opening deposit when the account was opened inside the window** (it was a venue transfer too, and the Alpaca sandbox cap is per account per day).
9. **Reset:** before archiving, the reset asks the venue to cancel every PENDING transfer that has a venue id (`cancelPendingAtVenue`, best effort; refusals and errors are logged at error level). `AccountService.archiveAndReprovision` then locks the account and runs archive hooks inside the archive transaction; the cash-transfers hook marks every PENDING transfer CANCELED ("Canceled by account reset"). The new account starts with no transfers. **No money moves on an archived account without an operator**, but a late venue settlement is never silent: the sweep watches reset-canceled transfers with a venue id for 7 days; a venue FAILED is stamped "(venue confirmed it never settled)", a venue SETTLED is logged as an error with transfer/account/venue ids and stamped on `failure_reason` ("…the venue settled it anyway. Operator review required.") — the correction is an operator ADJUSTMENT entry on the archived account (`divergedAfterReset` in the sweep result). The same applies when a venue answer reaches a PENDING row of an already-archived account.
10. **Net deposits** (equity series) = Σ DEPOSIT + Σ WITHDRAWAL (withdrawals are negative).

**API:** `GET /api/v1/account/cash` (summary + 20 newest transfers of the current account; 404 `NO_ACCOUNT`), `POST /api/v1/account/transfers` (header `Idempotency-Key: <uuid>` required; 201 new, 200 replay, 409 key reuse with a different body; DOMAIN_RULE subcodes `AMOUNT_TOO_SMALL`, `AMOUNT_TOO_LARGE`, `DEPOSIT_LIMIT`, `INSUFFICIENT_WITHDRAWABLE`, `ACCOUNT_NOT_ACTIVE`; VALIDATION `INVALID_AMOUNT`). Money is always a 2dp string.

**Rationale:** Posting on venue settlement keeps the invariant "ledger cash never exceeds venue cash" true by construction, as activation already does. Holding withdrawals inside the same lock that guards placement is the only way a withdrawal and a buy racing on the same dollars serialize correctly; the hold is derived from rows (Σ PENDING), never a cached counter, so it can't drift. A separate module keeps the paper feature from becoming an accidental first implementation of live funding.

**Consequences / open items:**

- **Outgoing ACH in the sandbox is unverified.** No write call was made against the real sandbox while building this; `tests/external/alpaca-transfers.smoke.test.ts` (`SMOKE_TRANSFERS=1`) verifies a $1 deposit and withdrawal end to end. Until it passes, withdrawals on the Alpaca venue may end FAILED (hold released, nothing posted — safe, but unhelpful). The venue's $50k/day cap may also count withdrawals; such a rejection surfaces as FAILED with the venue's message.
- **ACH returns after COMPLETE** (a `RETURNED` transfer that had already settled) are not re-polled: settled transfers are terminal locally. Recovery would be an operator ADJUSTMENT entry.
- **Negative-cash guard at settlement.** A withdrawal only settles if cash ≥ amount at that moment. Holds make this hold except when a market fill overran its reservation (the existing, documented MARKET-buffer case); then the transfer stays PENDING and the sweep logs an error every pass until an operator resolves it.
- A transfer that never got a venue id before a reset cannot be cancelled or watched at the venue (there is no id to name); if its initiate actually reached the venue, only the venue-cash comparison would show it.
- The deterministic venue keeps transfers in memory: a process restart between initiate and settlement leaves the row PENDING until the sweep fails it after the grace window ("no record").
- Paper only: the live-mode preview's funding sheets still send nothing (ADR-011); live funding remains `FundingProvider` + LIVE_TRADING_TODO.md.

**Revisit when:** the external smoke has exercised outgoing ACH (record the result in INTEGRATIONS.md), or when live funding is approved (it gets its own module behind `FundingProvider`, not this one).
