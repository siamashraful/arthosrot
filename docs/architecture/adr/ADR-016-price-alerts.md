# ADR-016 — Price alerts: one-shot, in-app, evaluated on fresh in-session quotes

**Status:** accepted (2026-10)

**Context:** Users asked to be told when a stock crosses a price ("AAPL above $210") without watching the screen. An alert is a notification about **display data** (the cached IEX quote the UI shows); it must never become an input to execution, reservations or the ledger. The hard parts are honesty and exactly-once: an alert must not fire on a price that is no longer true (a stale cached quote served through a provider outage, an at-close price overnight), and two evaluators racing (two job ticks, or the job and the user's own page load) must not fire it twice.

**Decision:**

1. **A new module `core/alerts`** (pure rules + `PriceAlertService`) with its own ports: `PriceAlertsRepository` and `AlertQuoteSource` (`Pick<MarketDataProvider, "getQuotes" | "getMarketStatus">`, satisfied by the cached provider). Depends on `market-data`, `money`, `shared` only. No broker, ledger, orders or accounts dependency.
2. **Table `price_alerts`** (migration 0007): `user_id` FK users (ON DELETE CASCADE: alerts belong to the user, so they survive an account reset), `symbol` (uppercase CHECK, validated through `InstrumentService.getOrRegister` and `status = 'ACTIVE'` at creation, like order placement; no FK to `instruments`, which another module owns), `direction` CHECK `ABOVE|BELOW`, `threshold NUMERIC(18,4)` CHECK > 0, `state` CHECK `ACTIVE|TRIGGERED|CANCELED`, `created_at`, `triggered_at`, `trigger_price NUMERIC(18,4)`, `trigger_quote_at`, `read_at`, `canceled_at`. CHECKs make the trigger facts all-or-nothing, required once TRIGGERED, absent while ACTIVE, `read_at` only after a trigger, and `canceled_at ⇔ CANCELED`. Indexes: `(state, symbol)` (the job's scan), `(user_id, created_at DESC)` (the list), and a **partial UNIQUE** on `(user_id, symbol, direction, threshold) WHERE state = 'ACTIVE'`.
3. **One-shot state machine:** `ACTIVE → TRIGGERED | CANCELED`, `TRIGGERED → CANCELED`, `CANCELED` terminal. Only ACTIVE is evaluated. **Re-arm is a new alert** with the same terms (`POST` again): a triggered alert never returns to ACTIVE, so its trigger price/time stay immutable history. Delete is a soft delete (CANCELED, row kept).
4. **Validation:** the threshold is a decimal string, ≤ 4 dp (Px precision), ≤ 10 integer digits, > 0; malformed or zero → 422 `VALIDATION`/`INVALID_ALERT_PRICE` (never coerced, no `parseFloat`). Up to **50 ACTIVE alerts per user** (`DOMAIN_RULE`/`ALERT_LIMIT_REACHED`); TRIGGERED and CANCELED don't count.
5. **Duplicates are idempotent, not 409:** creating an alert whose terms equal an existing ACTIVE alert returns that alert with `200 {created: false}` (a new one is `201 {created: true}`). Rationale: a double-tap or retry is not an error the user should see, and there is nothing to conflict about (no request body differs). Creation runs under a per-user transaction-scoped advisory lock (`pg_advisory_xact_lock`), so the cap and the duplicate check can't be raced; the partial UNIQUE index is the structural backstop.
6. **Trigger rule (pure, unit-tested, exact `Px.compare`):** inclusive at the threshold: `ABOVE` holds when `last ≥ threshold`, `BELOW` when `last ≤ threshold`. An alert triggers only when **(a)** the provider's market status is `OPEN` (regular session; pre/post-market and closed-market prices are shown, never acted on), **(b)** the quote was observed ≤ **15 minutes** ago (`ALERT_MAX_QUOTE_AGE_MS`; a cached quote served through an outage carries its old timestamp and fails this), and **(c)** the condition holds on the quote's `last`. **Gap rule:** a market that opens beyond the threshold triggers at the first fresh in-session quote, and the recorded `trigger_price` is that quote's `last` (the observed price, possibly beyond the threshold), with `trigger_quote_at` = the quote's own timestamp.
7. **Exactly-once triggering:** each trigger is a conditional `UPDATE … SET state = 'TRIGGERED', … WHERE id = ? AND state = 'ACTIVE'`. Concurrent evaluators block on the row; after the winner commits the loser re-checks `state = 'ACTIVE'` and matches nothing. A delete racing a trigger is serialized the same way.
8. **Evaluation drivers:** the worker job `price-alerts` (registry `defineJob`, interval `ALERTS_CHECK_INTERVAL`, default `5m`) gets the distinct symbols of ACTIVE alerts, checks market status once (off-session: returns without quoting), batches symbols (100 per call) into the **cached** provider from the container (sharing the UI's quote cache), evaluates and triggers. It throws only when no quote batch could be fetched, so the registry records the failure and retries. **Opportunistically**, `GET /api/v1/alerts` and `GET /api/v1/alerts/unread-count` evaluate the caller's own ACTIVE alerts first (never erroring on a provider failure), so alerts work in local/dev without the worker and fire promptly while the app is open.
9. **Notifications are in-app only:** an unread count (TRIGGERED with `read_at IS NULL`) drives a dot on the bell; the alerts sheet lists triggered + active alerts and marks the shown ones read on open. **Email (and push) is a later channel**, out of scope here.

**API:** `GET /api/v1/alerts` → `{alerts, unreadCount}` (ACTIVE + TRIGGERED, newest first, ≤ 200); `POST /api/v1/alerts {symbol, direction: "ABOVE"|"BELOW", price: "210.00"}` → 201/200 `{alert, created}` (422 `INVALID_ALERT_PRICE` / VALIDATION, 404 `UNKNOWN_SYMBOL`, 422 `INSTRUMENT_INACTIVE`, 422 `ALERT_LIMIT_REACHED`, 429 rate limit 30/min); `DELETE /api/v1/alerts/[id]` → `{alert}` (another user's, unknown, malformed or already-deleted id → 404); `POST /api/v1/alerts/read {ids?: uuid[]}` (empty body = all) → `{updated, unreadCount}`; `GET /api/v1/alerts/unread-count` → `{unreadCount}`. All `withAuth`, zod-validated, ownership-scoped. Prices are 4dp strings.

**Rationale:** Evaluating in core with `Px` keeps the one rule (inclusive, exact) testable and shared by both drivers; the conditional update makes idempotency structural instead of relying on job leases. Trusting only fresh in-session quotes keeps alerts honest about what the market actually did. Making alerts user-level (not account-level) means a paper reset doesn't silently drop them, and keeps them clearly outside paper financial state.

**Consequences / open items:**

- **Cadence rides the reconcile cron.** Jobs run when the worker runs due jobs — after every market-hours `/reconcile` (10-minute cron) and on the hourly `jobs.yml` tick. With `ALERTS_CHECK_INTERVAL=9m` (render.yaml) the job is due on every reconcile, so alerts fire within ~10 minutes in session with no extra cron. Off-hours `/healthz` may show the job overdue, like reconciliation staleness; alerts only fire on fresh in-session quotes anyway. The opportunistic read path still fires alerts within a minute for users with the app open.
- **IEX last price** is IEX-venue trades only (INTEGRATIONS.md): an alert can trigger slightly earlier/later than a consolidated-tape price would. The trigger price recorded is what the app displayed.
- **Pre-market edge:** a quote observed in the 15 minutes before the open is "fresh" at 09:30–09:45 ET; the status gate is the provider's market status, not the quote's own timestamp. Accepted (it is still a real observed price within 15 minutes).
- **Exchange holidays** are not modeled by the calendar approximation (LIMITATIONS.md); on a holiday the live provider's quotes are old, so the staleness rule holds alerts.
- The client refuses an alert its current price already meets (an "above" at or under the last price); the server accepts it (it would trigger on the next check) because the server's quote may differ from what the page showed.
- Email notifications, alert editing, percentage-move alerts and per-alert expiry are not built.
